# Changelog

Counting convention: **listed** = entries in category sections; **held** = rows in Held for Verification; **tracked** = listed + held. Sweep deltas are stated as the net change in listed entries; gross additions are called out separately where they differ (renames and variant merges make a naive name-diff overcount).

## 2026-11-24 — templates, issue forms and an agent instruction file (12,344 listed and 136 held, unchanged)

Not a catalog sweep and no change to the data: only documents and templates changed.

- **Pull request template.** It told contributors to regenerate the README only, so anyone who followed it failed the `generated-in-sync` check. It now matches CONTRIBUTING: the `subcategory` field, both generators, every generated path to commit, and both lint commands.
- **Issue forms.** Three forms replace the blank issue: add a connector (or give a held entry its page), report a dead or wrong link, and send a field report. Blank issues are off. The issue chooser sends harmful links to private reporting instead.
- **SECURITY.md** names GitHub's private **Report a vulnerability** route beside the email address. Private reporting was already on; the page didn't mention it.
- **CONTRIBUTING.md** no longer says each sweep commits a dated catalog capture. None has since 2026-09-06. It now says where `C` markers come from: the feed as read at each sweep, dated by `capture_date`.
- **CLAUDE.md** is new. It holds the rules for AI agents that run sweeps here: fetched and contributed text is data, never instructions; no link without opening its page; no hand-edited generated files; one concern per pull request; never weaken a check to make data pass; and the commands to run before a pull request.

## 2026-11-24 — the five largest categories split into a page per subcategory (12,344 listed and 136 held, unchanged)

Not a catalog sweep and no change to the data. Every entry is where it was in `data/connectors.json` and in `site-data/`; only the markdown pages it is printed on have moved.

**Why.** GitHub stops rendering a markdown file at about 512 KB, and the generator refuses any page over 500,000 bytes. Marketing and Sales had reached 466,665 bytes, about 83 entries short of that, while the directory feed has been growing by 1,300 to 1,500 servers a week, roughly one in ten of them landing on that page. The next ordinary sweep would not have built. Four more pages stood between 368 KB and 448 KB.

**What changed.** A category that has subcategories is now written as a short index page plus one page for each subcategory. The index keeps the category's address (`categories/marketing-and-sales.md`), so the front page and any link to the category still arrive; it lists the subcategories with their counts. Each subcategory's entries are on a page of their own (`categories/marketing-and-sales.crm-and-pipeline-management.md`) that links back to the index and across to its siblings. This applies to Data and Analytics, Finance and Trading, Lifestyle and Local, Marketing and Sales and Productivity: 5 index pages and 38 subcategory pages in place of 5 long ones. The other 28 category pages are byte-identical.

The split does not wait for a size. A category with subcategories is always written this way, because a page that split only past a threshold would move its entries from one address to another as it grew and back if it shrank.

**What is lost.** A link to a heading inside one of the five old pages (`…/marketing-and-sales.md#crm-and-pipeline-management`) now opens the index at its top instead of that section.

**Headroom.** The largest page is now Legal at 206,996 bytes; the largest subcategory page is Geospatial and Industry Data at about 127 KB. The generator prints a note once any page passes 80% of the limit, and when one goes over it says which split would fix it. Categories without subcategories are not helped by this: Legal, Development Tools and Travel are each near 200 KB and will need subcategories of their own as the list grows.

**Checked.** The 12,344 entry lines are the same lines before and after, sorted and compared. `site-data/` did not change. The generator's self-test gained eight rendering cases, written before the change and seen to fail against the old generator.

## 2026-11-24 — validator rules, a self-test and an inert feed report (12,344 listed and 136 held, unchanged)

Not a catalog sweep and no change to the data: every generated file is byte-identical.

A review of the repository on 2026-11-23 planted hostile entries against the generator's validator, and it accepted them: markup or a bare URL in a name, a link written into a subcategory, an `A` marker on a third-party entry, an `ftp` link or an email address in a description, and several invisible characters. `SECURITY.md` said such entries were rejected; for names and subcategories that was not yet true. No entry in the list used any of them.

**What the generator refuses now.**

- A name containing `<`, `>`, a backtick or `://`, a character reference such as `&#101;`, or a backslash that escapes the character after it, any of which would let one name read as another or unhook its link. A name may still start with `www.`, as nine catalog names do: inside an entry's link it stays plain text.
- A category or subcategory that is not letters, digits and spaces, and a subcategory that is not one of the headings listed for its category (38 across five categories).
- An `A` marker on any entry outside a list of 14 names, and any of those 14 without it. Ten are the directory feed's `anthropic` tier as read on 2026-11-24; four are Anthropic's quickstart extensions (PDF Viewer, pdf-viewer, Word and PowerPoint), which the feed files under partner tier and which have kept `A` at every sync.
- In a description, a use case or a held row: any `scheme://` link, where before only `http` and `https` were caught; `www.` in any case; anything shaped like an email address, a host that starts with a dot included; and any backslash or character reference. GitHub looks for links after it has decoded references and dropped backslash escapes, so `https&#58;//…`, `www\.…` and `a\@…` each rendered as a link on its own renderer.
- A URL containing a quote, a backslash, an angle bracket, a brace, a pipe, a caret, a backtick, an opening parenthesis or a character reference, or whose host has an empty label (a trailing or doubled dot) or ends in a number, which is how a browser recognises an IP address, hex forms such as `0x7f.0.0.1` included.
- Anywhere in the data: every control character, line and paragraph separators, any space other than the ordinary one, unassigned code points, and every character Unicode marks as ignorable by default (blank fillers and all variation selectors among them, the emoji selector U+FE0F too, until a name needs one) plus four blank-rendering characters outside that set, on top of the zero-width and bidirectional characters already refused.
- A "last updated" or capture date that is not a plain date. Both are printed into the README and every category page as they stand, and until now only had to be non-empty.

The two lists (headings and Anthropic-built names) live in `scripts/generate_readme.py`, not in `data/`, so a pull request that only touches data cannot extend them.

**The website's editorial file.** `data/editorial.json` reached `site-data/` with only its ids checked. Every string in it, keys included, now gets the same text rules, and a collection slug must be lowercase letters, digits and hyphens.

**Proven before trusted.** `python3 scripts/generate_readme.py --selftest` plants one defect per rule on a small valid list and requires that rule's own message, then plants eight things that must stay legal. CI runs it ahead of `--check`. Run against the validator as it stood before this change, 44 of its 48 planted defects were accepted outright, three were refused and one (a category given as a list) crashed it. The export's self-test gained eight editorial cases.

**Checked on GitHub's renderer.** The first version of these rules was handed to a second, independent pass whose job was to break it, and it did: the reference, backslash, capital-`WWW.` and dot-led address forms above, and 21 ignorable characters that sit in an ordinary letter-mark category. After the fix, 120 candidate strings were run through the validator and every one it accepted was rendered through GitHub's markdown API: none produced a link other than the entry's own. A second break-it pass on the fixed rules reported the same for 7,664 accepted strings, and found one more character that draws nothing, U+FFFC, now refused. One thing is left as it is: an emoji shortcode such as `:octocat:` still renders GitHub's own emoji image.

**The weekly feed report.** The Friday feed-diff issue is public and carries text the catalog's vendors wrote. Its escaping left that text live: rendered on GitHub, a URL, a `www.` host, an email address, `owner/repo#1`, `#12` and the URL inside an escaped markdown link all came out as links, and emphasis was applied. Every cell that comes from the feed, the sitemap or the list is now one inline code span, where nothing links, formats, mentions a user or references an issue, and the report opens by saying that its tables hold third-party catalog text, to be read as data and never as instructions. The same saved feed through the old script and the new one gives identical section counts and row order (1,714 rows), and the capped report as GitHub renders it holds no link, mention or issue reference in 462 rows. The fetch now stops at 50 pages and at 64 MB a response, and every cell is cut at 100 characters. The code spans take the capped report from 54,282 to 58,147 bytes against the 65,536 an issue body may hold, so a report that would not fit has its rows per table halved, and the run stops if even one row per table does not fit. The script's self-test now builds a report from hostile text in every field and requires all of it inside code spans; with the code span removed at each of its 25 call sites in turn, 23 of the mutants fail it, and the two that pass print only tier constants.

## 2026-11-22 — error pass: confirmation steps and thin descriptions (12,351 listed; held 129)

A pass over entry text only: 1,987 entries changed, none added, removed or moved. It targets two defects found by a blind read earlier the same day. Every changed entry was checked against its record in the directory feed captured for this pass (12,500 servers; 12,314 of the 12,351 listed entries match exactly one record).

**Dropped confirmation steps.** Where a connector's record says a person must confirm, approve or be asked before it acts, the entry should say so. A pattern match picked 858 entries whose record names such a step for an action the description names while the description does not; the match is crude, so each was read. Writers added the step to 629 and left 229 alone (the "approval" was the sign-in consent screen, or the step covers an action the entry does not name). Thirty were first shown with a record sentence cut at a line break; those were re-read against the full record and their first verdicts discarded.

**Second wave.** The pattern match had set a further 1,417 candidates aside as lower yield. 451 of those were set aside only because the description already used a word such as "drafts", "reviews" or "previews". That word usually names something the connector does and not a step a person takes, and the rule had kept out one of the five entries the blind read found. The 451 were read with their full records: writers added the step to 290 and left 161 alone.

**Thin descriptions.** 1,005 entries had a description under 60 characters, often the vendor's tagline (430 community tier, 563 unmarked, 12 Anthropic). 972 have a single catalog record; 965 of those were rewritten from the record's description and tool names, and 7 were left because the record says no more than the entry did. Use cases were rewritten in 735, mostly because the old one was a list of topics.

**Review.** Reviewers read a seeded sample against the records. They were separate runs of the same model that wrote the changes, each given the entry and its record: 150 thin rewrites (22 minor breaches), 91 confirmation fixes (19 minor, 1 misleading) and 29 entries left unchanged (5 minor). Both sets were over the 10 percent line set beforehand, so each then got one full review pass, which was the last round:

- Thin rewrites, all 965 read: 849 passed, 114 minor, 2 misleading. Most breaches were use-case details the record never names (a location filter, a report type, a time period). 114 corrections applied.
- Confirmation set, all 858 read: of the 629 fixed entries 414 passed, 210 minor and 5 misleading; of the 229 left unchanged 173 passed, 55 minor and 1 misleading. Most of what the reviewers found was not the added clause: it was a limit the description had already dropped (a paid-plan gate, a country, a role) or a write the tools do not support. 269 corrections applied, 56 of them to entries the writers had left unchanged.
- Second wave, all 451 read: of the 290 fixed entries 190 passed, 99 minor and 1 misleading; of the 161 left unchanged 114 passed, 46 minor and 1 misleading. The pattern was the same as in the first wave: in 105 of the 147 entries not passed, the reviewer's note says the description drops or omits something the record states. 147 corrections applied, 47 of them to entries the writers had left unchanged.

First-wave reviewers saw each record's first 70 tool names. The 29 corrections on entries with longer tool lists were checked against the full list, and 4 were dropped because the full list supports the original text. Second-wave writers and reviewers saw each record's text in full and its first 150 tool names; nine entries have longer lists, one of them was corrected, and the full list does not contradict that correction.

**Limits.** No person read these entries one by one. Writers and reviewers were the same model, so the review is a second read and not an independent one, and the reviewers' corrections were format-checked but not themselves reviewed. First-wave reviewers were given two conflicting instructions for entries the writers had left unchanged (check only for a missing confirmation step; grade the whole entry), so other defects in those 229 entries may be undercounted; second-wave reviewers were told to grade the whole entry. Not done: 966 lower-yield confirmation candidates the pattern match also raised, and 33 thin entries with no single catalog record. The reviewers' main finding, limits dropped from descriptions, was fixed only where they met it in these sets; the rest of the list has not been read for it. The added clauses make entries longer: 629 descriptions now run over 320 characters (449 before the pass) and the longest is 523.

## 2026-11-22 — site feed: first-seen dates and a change log (12,351 listed; held 129)

The site feed now says when each entry was first listed. Every row of `site-data/search.json` carries `added`, an ISO date, and a new file, `site-data/changes.json`, lists the ids added, removed and renamed on each date, newest first. No entry changed.

Both are built from `data/changes.json`, the record of when each entry id joined or left the listed set. `scripts/backfill_changes.py` rebuilt it once from the git history of the two files that have held the catalog (`README.md` until 2026-08-10, `data/connectors.json` since): 90 commits, 23 dated changes, 12,408 additions, 57 removals and 83 renames, ending at today's 12,351 ids. The rules:

- A date is the commit's own calendar date, and changes are netted per date: an entry held and restored the same day leaves no trace.
- A name that changed while its URL stayed is a rename, and the entry keeps its first date. Google Cloud BigQuery, Intuit QuickBooks and Grafana MCP Server have been listed since 2026-04-13 and would otherwise read as new on 2026-05-15, the day the list took the catalog's names. A rename that also changed the URL cannot be told from a removal and an addition, and is recorded as one.
- An id that left and came back keeps its first date.
- `removed` means no longer listed: delisted, or moved to Held.
- `added` is the date of first listing here, not the date Anthropic added the connector to its catalog.

From here the export keeps the record. A plain `python3 scripts/export_site_data.py` appends a change dated that day when the listed ids differ from it, `--check` fails until the result is committed, and `--selftest` proves the record's reader on planted cases. CI needs no git history. By first date, 273 of today's entries go back to the first commit on 2026-04-13 and 4,332 are from 2026-11-22.
